# 分解动画与相机恢复审计

日期：2026-10-26。对象：用户提供的《屏幕录制 2026-10-26 200033.mp4》，圆弧形楼梯构造。

## 结论

问题成立：模型收起后，构件恢复装配状态，但相机仍停留在展开时拉远的距离。模型的屏幕占比没有恢复。

已解码并逐帧检查全部 346 帧（30 fps，11.533 秒）。8 张连续联系表覆盖每一帧；另保存逐帧图像、测量 CSV/JSON 和可拖动的帧查看器。

## 画面证据

| 时间段（约） | 画面状态 | 判断 |
| --- | --- | --- |
| 0–0.8 秒 | 初始装配状态 | 模型轮廓约 320×363 像素 |
| 0.8–4.8 秒 | 展开，构件向外移动，相机逐渐后退 | 为容纳展开后的范围，模型投影变窄 |
| 4.8–5.6 秒 | 展开完成 | 轮廓约 258×377 像素 |
| 5.6–9.6 秒 | 收起，构件回到原处 | 模型宽度仍基本锁在 258 像素，没有随范围缩小而拉近 |
| 9.6–11.5 秒 | 收起完成后静止 | 仍为 258×291 像素；等待约 1.9 秒没有恢复 |

测量在原录像的 1/2 分辨率图像上进行，同一固定模型区域，未对模型单独缩放。灰度阈值与连通区域过滤排除鼠标等小片段；中间帧数据用于趋势判断，受抗锯齿与压缩影响。首尾装配姿态的对比最有说服力：

- 宽度恢复率 80.6%，高度恢复率 80.2%，约小了 20%。
- 首帧包围轮廓中心约 (658,451.5)，末帧约 (660,451.5)，中心基本一致。
- 因此主要异常是相机距离未恢复，而不是页面区域变小或整体偏移。
- 录像开始时页面已经打开，不能仅凭录像证明此前是否有手动相机交互；这一触发条件另外进行了本地复现。

## 代码定位与本地复现

1. `src/components/viewer/ModelViewer.tsx:1663` 的 `handleControlsStart` 直接把 `_userCameraInteracted` 设为 true，没有判断是否实际发生旋转、平移或缩放。
2. 本地 `three-stdlib/controls/OrbitControls.js:701` 在鼠标按下进入交互状态时发送 start 事件，不需要等待鼠标移动。所以单击模型区域也会进入“手动相机已操作”状态。
3. `ModelViewer.tsx:1095–1097` 在该状态下使用 `Math.max(currentDistance, boundsFit.finalDistance)`。展开时可以拉远；收起时即使所需距离减小，也永远不能拉近，形成距离只增不减的行为。
4. `ModelViewer.tsx:1091` 又把该状态的后续更新限制在 `animationChanged`。动画到达 0 后进度不再改变，缺少完成后的持续收敛阶段。
5. 当前只有重新挂载或显式适配/重置等路径清除手动标记；收起动画本身没有恢复自动适配状态。

复现步骤：打开圆弧形楼梯 → 暂停自动旋转 → 保存基准截图 → 单击画布空白处一次（不拖动、不滚轮）→ 完整展开 → 完整收起 → 保存截图。已复现收起后变小，视角保持不变。证据为 browser-before.png、browser-expanded.png、browser-after.png。

这是单模型节点共用的 CameraTracker 分支，具有共同触发条件的单模型节点也会受影响。多模型在 `variantCount !== 0` 时跳过此分支，本次没有证明多模型存在相同问题。当前审计未修改业务代码、模型或相机参数。

## 建议修复逻辑

将“用户选择的视图”与“分解动画临时拉远量”分开管理。

1. 单击选构件不应永久关闭自动适配；只有实际相机位移/缩放才记录用户视图变化。
2. 记录展开前的视图基准，展开时按实时边界增加安全距离；收起时双向平滑回到该基准，不使用只增不减的距离钳制。
3. 进度停止后仍持续收敛，直到距离和观察中心误差进入阈值；不要依赖进度必须变化。
4. 保留用户的观察角度。如果用户主动缩放，应保存其缩放意图；动画只移除自己增加的临时距离，不覆盖用户选择。
5. 区分终点：展开完成（进度 1）应保持展开范围的合适大小；收起完成（进度 0）才恢复装配状态的基准大小。界面宽度改变时应按新区域重新计算。
6. 验收应覆盖：无相机操作、仅单击、实际旋转、手动缩放、中途反向、滑块跳转、连续多轮展开收起，以及不同画布宽高。收起后同姿态的投影尺寸应接近展开前，且不能逐轮变小。

建议保留现有首屏大小和旋转角度；此次修复只处理分解过程的临时距离与结束后的恢复。
